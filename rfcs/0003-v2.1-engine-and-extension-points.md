## 1. Summary and Motivation

### Summary

Make RGL v2 do what the v2 epic (#346) promised and did not fully deliver. The work has four parts:

1. **Golden masters first.** Pin current behavior, bugs included, in all three repos before changing any code. Tag each known bug `knownBug`, so every later fix shows up as a reviewed golden diff.
2. **One pure engine.** Today there are three interaction state machines: `GridLayout`, `useGridLayout` and `ResponsiveGridLayout`. Replace them with a single pure reducer in `src/core` that both `GridLayout` and `useGridLayout` drive.
3. **Typed extension points.** Add slots and hooks as plain objects or functions on the existing strategy pattern (`Compactor`, `PositionStrategy`, `LayoutConstraint`). Each one is testable in Jest without React. There is no `plugins=[]` registry.
4. **Measured performance and clarity work.** Fix the hot paths the audits measured, with a committed benchmark baseline. Delete dead and duplicated code.

It ships in two minors, each first as a release candidate on `next` (§15). **2.4.0** carries parts 1 and 4, the bug fixes and the input and work bounds (§14), with no engine. **2.5.0** carries parts 2 and 3.

The public API gains optional fields and new exports only; no existing type changes (§12). Behavior changes are limited to bug fixes, the input bounds and the mutation policy. Each one is listed in the triage table or §12 with its changelog handling.

#### What the audits found

Four problems account for most of the findings.

1. **Three engines that drifted apart.** `GridLayout.tsx` (1346 lines) holds config resolution, layout sync, change notification, the drag, resize and drop controllers, the touch adapter and placeholder rendering (rgl-react §3.1). `useGridLayout` is a separate implementation that `GridLayout` never calls. It loops forever on an inline layout literal (`react/hooks/useGridLayout.ts:207-221`) and fires `onLayoutChange` on every drag move (rgl-react §4.9). Every new hook added today would need two implementations.
2. **Mutation where the docs promise immutability.** `moveElement` mutates the live state item (`core/layout.ts:290-292`). That corrupts `oldLayoutRef` (`GridLayout.tsx:548`) and causes a spurious `onLayoutChange` after a drag that ends where it started (rgl-core B2). The classic compactors mutate their input, and the output depends on that mutation (`core/compactors.ts:64-71`; rgl-core M1). RFC 0001's principle 3, "Immutable by default", does not hold.
3. **Hot paths that scale badly.** One drag frame at 500 mixed-size items takes 48 ms in core alone (rgl-core §3.1), three times the 16 ms frame budget RFC 0001 set (`rfcs/0001:1527`).
4. **Closed extension points.** Closed unions (`core/types.ts:264,318`), a key whitelist that drops custom item fields (`core/layout.ts:81-99`), and render paths with no slots (`GridLayout.tsx:1271`).

The maintainer's brief for this work: extensive golden-master and integration testing in all three repos, then serious work on performance and clarity, with extension points broad enough that third-party libraries can add almost anything.

### Design Principles

RFC 0001's five principles stand. This RFC makes principles 1 and 3 true in the code, and adds five more.

6. **Pin before you change.** No refactor lands without a golden suite that covers the code it touches. A behavior change is a golden diff, reviewed like code.
7. **One engine.** Interaction state lives in one pure reducer, in grid units. Components render that state and translate DOM events into grid-unit actions. Nothing else.
8. **Every extension point is a plain value.** An object or a function with typed inputs and outputs. A Jest test without React or a DOM can exercise it. No registry, no ordering keys, no lifecycle beyond what the type says.
9. **Defaults are the extension points.** Built-in behavior goes through the same interface a third party would use: `verticalCompactor.resolveDrag` is the default drag resolver, not a special case.
10. **Measure, then optimize.** Each performance PR states its baseline and target from the committed benchmark JSON.

## 2. Non-Goals

- **No breaking changes to the public API.** Positional callback arguments, prop names, exported symbols and their signatures all stay, including their TypeScript types (an API report and consumer compile tests enforce this, §11). `Compactor.type` stays a closed union (§4 rank 2). Removals wait for v3.
- **No generic plugin registry.** The pluggability survey found no case that ordered arrays of typed strategies cannot cover (pluggability §3, §5). TipTap-style priority ordering is the cost a registry brings.
- **No virtualization.** Searches for "virtualization OR virtualize" returned 0 issues (pluggability §2).
- **No undo/redo feature, and no built-in adapters for external stores (redux, zustand).** No demand was found (pluggability §2). The `detail.source` tag plus a controlled `layout` is enough to build either outside the library.
- **No CSS Grid or flexbox layout mode.** That would be a new `PositionStrategy`, possible after this RFC, not part of it.
- **No rewrite of react-draggable or react-resizable in 2.x.** Their bugs get fixed upstream, and RGL talks to them through internal translation functions (§3, §8).
- **No change to the legacy v1 API surface**, other than fixing places where the legacy wrappers already break v1 behavior (RX-13 in §7).
- **No freezing or readonly typing of exported default singletons.** Someone may mutate `defaultConstraints` today (`core/constraints.ts:384`), and `applyPositionConstraints` takes a mutable `LayoutConstraint[]` (`core/constraints.ts:403-405`). Both wait for v3 (rgl-core X16).
- **No engine export from `react-grid-layout/core` in 2.4.0 or 2.5.0.** It stays internal until the store goes public (§3, §4 rank 14).

## 3. Architecture

The engine, the store and the binding in this section ship in **2.5.0**. 2.4.0 changes no architecture: it adds tests and CI, fixes bugs in place, bounds untrusted input and refactors `src/core` (§9). The module tree marks the release that touches each file.

### Target picture

```
 DOM events          React binding (src/react)
 ----------          ------------------------------------------
 mouse, touch  --->  RD / RR translation, getClientPoint
 keyboard            activation (distance, delay)
 HTML5 drop          px -> grid units (rect, scroll, grab, scale)
 touch drop          live pixel box of the active item (local)
                     ignore-until-release after a rejected start
                          |                        ^
                          | GridAction             | selected state
                          | (grid units)           | + GridEvent[]
                          v                        |
 +---------------------------------------------------------------+
 | core engine (src/core/engine): pure, no React, no DOM types    |
 |                                                               |
 |   reduceGrid(state, action) -> { state, events }              |
 |                                                               |
 |   propose -> constraints -> onProposal -> resolveDrag or      |
 |   resizeElement -> compact -> onResolved -> working layout    |
 |   stop -> the same stages on the last proposal -> commit      |
 |        -> layoutChange (at most once)                         |
 +---------------------------------------------------------------+
```

The engine is a reducer, not a class. Its state is plain data in grid units. The React binding owns DOM measurement, pointer math and event translation. The engine owns every decision about where items go.

### Where the engine lives

The audits proposed two locations: `src/react/state/gridReducer.ts` (rgl-react §3.4) and `src/core/engine.ts` (pluggability §3.0). This RFC picks **`src/core/engine/`**. It must be pure and testable without React (principle 8), and `src/core` is the folder that promises that. The React binding (`createGridStore`, `useGridStore`) lives in `src/react/state/`.

The engine is **not exported** from `react-grid-layout/core` in 2.5. Exporting `reduceGrid` would freeze `GridEngineState` and `GridAction` as public API, which is the same reason the store stays internal (§4, Later). Non-React callers who need constraints get the pure functions that are already exported (`applyPositionConstraints`, `applySizeConstraints`, `core/constraints.ts:403,450`).

### Engine config

```ts
// src/core/engine/types.ts
export interface EngineConfig {
  readonly cols: number;
  readonly maxRows: number;
  readonly rowHeight: number;
  readonly margin: readonly [number, number];
  readonly containerPadding: readonly [number, number] | null;
  readonly containerWidth: number; // the `width` prop
  readonly isBounded: boolean;
  readonly isDraggable: boolean;
  readonly isResizable: boolean;
  readonly compactor: Compactor;
  readonly constraints: readonly LayoutConstraint[];
  readonly middleware: readonly InteractionMiddleware[];
}

export function sameConfig(a: EngineConfig, b: EngineConfig): boolean;
```

`EngineConfig` holds the strategies and the geometry that `ConstraintContext` needs (`core/types.ts:361-382`), plus `containerPadding`, which `ConstraintContext` lacks today. It holds no user callbacks and no DOM types. The one per-gesture DOM measurement, the container height for bounded resize, rides on the `start` action instead (T9). The input bounds are constants in `core/validation.ts` (§14), not config.

**Config equality.** `sameConfig` compares field by field:

| Field                                                                                       | Equal when                                                                                                                          |
| ------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| `cols`, `maxRows`, `rowHeight`, `containerWidth`, `isBounded`, `isDraggable`, `isResizable` | SameValueZero                                                                                                                       |
| `margin`, `containerPadding`                                                                | both `null`, or the same length and each element SameValueZero                                                                      |
| `compactor`                                                                                 | the same `type`, `allowOverlap`, `preventCollision` (`undefined` reads as `false`), `compact` reference and `resolveDrag` reference |
| `constraints`, `middleware`                                                                 | the same length and each element the same reference                                                                                 |

The binding dispatches `setConfig` only when `sameConfig(next, lastDispatched)` is false. An inline `gridConfig={{margin:[10,10]}}` is therefore not a change, and it never triggers `RGL_W003`. A middleware or constraint object rebuilt on every render (`middleware={[snap(5)]}`) is a new reference, so it is a change. The docs say to create those once, at module scope or in `useMemo`. Mid-drag such a change waits in `pending.config` and applies at the flush without a warning, because it changes none of the fields below.

An idle `setConfig` always stores the new config. It re-syncs and commits only when `cols`, `maxRows` or the compactor key changed. The same three fields are the one rule for `RGL_W003` on a config: a pending `setConfig` applied at the flush warns only when it changed `cols`, `maxRows` or the compactor key. A width change or a rebuilt middleware array mid-drag applies silently. §10 and §15 point here.

### Engine state

```ts
export type InteractionKind = "drag" | "resize" | "drop";
export type InteractionSource = "pointer" | "keyboard";
export type InteractionPhase = "start" | "move" | "stop";
export type Proposal = DragProposal | ResizeProposal;

export interface ActiveInteraction {
  readonly interactionId: number; // assigned by an accepted start
  readonly kind: InteractionKind;
  readonly source: InteractionSource;
  readonly itemId: string;
  readonly handle?: ResizeHandleAxis; // resize only
  readonly containerHeight?: number; // from start, when isBounded
  readonly startItem: LayoutItem; // cloned at start
  readonly startLayout: Layout; // cancel target, minus removed items
  readonly workingLayout: Layout; // last accepted step, not committed
  readonly placeholder: LayoutItem; // set by start (below)
  readonly lastProposal: Proposal | null; // last accepted proposal
  readonly produced: readonly Layout[]; // startLayout + last 4 shown
}

export interface PendingSync {
  readonly layout?: Layout; // latest syncProps or setLayout
  readonly itemIds?: readonly string[];
  readonly config?: EngineConfig; // latest setConfig
}

export interface GridEngineState {
  readonly config: EngineConfig; // frozen while active is set
  readonly layout: Layout; // committed, compacted
  readonly active: ActiveInteraction | null;
  readonly lastNotifiedLayout: Layout; // baseline for layoutChange
  readonly pending: PendingSync | null;
  readonly nextInteractionId: number;
}
```

- **One config.** `state.config` cannot change while `active` is set, because `setConfig` goes to `pending.config` then. Every step reads `state.config`. There is no per-interaction copy.
- **Interaction ids.** The reducer assigns `nextInteractionId` on an accepted `start` or `nudge`, then increments it. A rejected start assigns nothing. The counter lives in state, so replayed action lists give the same ids and the replay goldens stay deterministic. The binding reads the id from the `start` event that `dispatch` returns.
- At start, an accepted `start{kind:"drag"|"resize"}` sets `placeholder` to `cloneLayoutItem(startItem)` and leaves `lastProposal` `null`, which still marks a click after activation at stop. `start{kind:"drop"}` sets `lastProposal` to `at` and `placeholder` from its start step, so a drop released in its entry cell runs the stop pipeline. After that, `lastProposal` changes only on an accepted `propose`. A step dropped by a veto, a `null` from `resolveDrag` or a throw leaves it alone, so a release after a rejected move re-runs the last accepted proposal, never the rejected one.
- **`produced`** holds the layouts this interaction handed to a consumer. It starts as `[startLayout]`, because `onDragStart` passes the start layout and a controlled parent may echo it. Each accepted step appends its `layoutResolved` and its `workingLayout`, skipping a layout that is `sameInput`-equal, by id, to one already held. Beyond `startLayout` it keeps the last 4 distinct layouts and drops the oldest, so it never holds more than 5 and a flush compares in O(k·n) with k = 5, however long the drag runs. Four covers a parent that renders a few moves late. Today `onDrag` and `onResize` receive the layout before compaction as argument 1 (`onDragProp(newLayout, ...)` at `GridLayout.tsx:584`, `onResizeProp(finalLayout, ...)` at `:747-754`), and §4 keeps that argument, so a controlled `onDrag={l => setLayout(l)}` echoes `layoutResolved`, not `workingLayout`. A same-cell move adds nothing. Only the echo rules read it (queue rules 3 and 5).
- There is no version counter. `layoutChange` is decided by one comparison at the commit boundary, against `lastNotifiedLayout`.

All coordinates are grid units. The binding converts pointer pixels before it dispatches.

- **Identity.** `propose`, `stop` and `cancel` carry the `interactionId` of the interaction they belong to. A gesture uses the id its `start` returned. A cancel the binding raises without a gesture of its own (`interactionKey`, effects re-running, the drop controller) reads `active.interactionId` from the snapshot. When it differs from `active.interactionId`, or `active` is `null`, the action is a no-op: the same state, plus one `warning` event `RGL_W011`, which the binding shows in development once per grid. A keyboard nudge, a second pointer, a second drop source or a hook `onDrag` for another id therefore cannot drive someone else's interaction (§10).
- **A `start` while `active` is set** is rejected: the same state, no events, no id. The binding sees no `start` event and puts that gesture in the ignore-until-release state, so it never dispatches a `propose` for it.
- **Nudge** is one atomic action. While `active` is set it is a no-op with no events. Otherwise the reducer checks permission with the same function as a pointer start (below), assigns an id and runs start, one step and stop through the full pipeline with `source: "keyboard"`. A resize nudge uses `se` geometry. The result commits at once. A rejected nudge is atomic too: when the permission check, a veto, a `null` from `resolveDrag` or a throw rejects it, the reducer returns the previous state, `nextInteractionId` included, and emits no interaction events at all, so no `onDragStart` fires without its stop. A throw still emits its `error` event. `NudgeDelta` is a discriminated union, so a delta that mixes move and size fields does not type-check.
- **The stop pipeline.** `stop` runs the full pipeline once more on the last proposal (constraints, `onProposal`, `resolveDrag` or `resizeElement`, `compact`, `onResolved`) and commits that result. The proposal is `stop.to` when given, else `active.lastProposal`. A stop with neither (a click after activation) runs nothing and commits `startLayout` unchanged. At stop, `resolveDrag` returning `null` commits the last accepted working layout, middleware returning `false` is a cancel with `vetoed`, and a throw is a cancel with `error`.
- **Same-cell moves.** A `propose` whose `to` equals `lastProposal` returns the same state and emits one `move` event. So `onDrag` still fires on every pointer move, as `GridItem.tsx:565` does today, while the store selector sees no change (T7).
- **Drop.** `start{kind:"drop"}` creates the placeholder `{i: item.i ?? "__dropping-elem__", x: at.x, y: at.y, w, h, data}` in `workingLayout` and runs the start step on it. The placeholder lives only in `workingLayout`. At stop, after the pipeline: with `dropId` (the hook path) the placeholder is renamed to that id, as `useGridLayout.ts:414-425` does today, and the result commits. Without it (the `GridLayout` path) the `onDrop` mapping receives the working layout and the placeholder item, as `commitDrop` passes them today (`GridLayout.tsx:1037-1042`), and the commit is the working layout minus the placeholder, recompacted (`GridLayout.tsx:921-927`). The placeholder id never reaches `state.layout`, `lastNotifiedLayout` or a `layoutChange` payload (#2210, `GridLayout.tsx:511`). A cancelled drop fires no `onDrop`.
- **`syncProps.layout`** is built by the binding: the `layout` prop plus one item built from each child's `data-grid` (`GridLayout.tsx:248-249`), through `itemFromDataGrid` in `core/engine/sync.ts`, then `validateLayoutInput` (§14). That keeps today's `data-grid` result and covers children added mid-drag.
- One permission function decides whether an item may start, for pointer and keyboard starts alike. A boolean `item.isDraggable` (drag, move nudge) or `item.isResizable` (resize, size nudge) wins over the grid's `isDraggable` or `isResizable`. Without one, a `static` item is blocked and the grid setting decides. That is today's rule (`GridLayout.tsx:1180-1186`), and the drag override is the one `moveElement` honors (`core/layout.ts:277`). The reducer tests cover both override directions for each kind: an item with `isDraggable: true` in a grid with `isDraggable: false`, and an item with `isDraggable: false` in an enabled grid, plus the same pair for `isResizable`.

### What commits

"Commit" means `state.layout` changes and the notification comparison runs. Moves never commit, so `onLayoutChange` never fires mid-drag. That keeps today's rule at `GridLayout.tsx:501-504`, which suppresses the notification while `activeDrag` or `droppingDOMNode` is set.

### Queue rules for an active interaction

1. **The active item is removed** (drag and resize only). A `syncProps` whose `itemIds` lack `active.itemId` cancels with `itemRemoved`. The cancel target is `startLayout` minus that item, so the stop callback's layout never contains it. Then the sync applies as an idle sync. A drop is exempt: its placeholder has no child, so `itemIds` never contain it. During a drop, a child removal follows rule 2, every other change follows rule 3, and the drop continues.
2. **Another item is removed.** The removal applies at once to both `workingLayout` and `startLayout`, and the step re-runs on `lastProposal`, so the dragged item can move into the freed space. With `lastProposal === null` nothing re-runs. A re-run emits no `move` event and appends nothing to `produced`. A later stop or cancel can never bring the item back.
3. **Everything else** in a mid-interaction `syncProps` or `setLayout` is checked in this order. All comparisons here match items by id (§3 comparisons).
   1. A current echo: `itemIds` equal the current ids and `layout` is `sameInput`-equal to the latest step's `layoutResolved` or `workingLayout`. It clears `pending.layout`, because the parent has taken the drag result and nothing newer is waiting.
   2. A data-only update or an earlier echo: `itemIds` equal the current ids and `layout` is `sameGeometry`-equal to `state.layout` or to any layout in `active.produced`. It carries no geometry. The reducer patches each item's `data` reference, by id, onto `state.layout`, `active.startLayout`, `active.workingLayout`, every `produced` entry and an existing `pending.layout`, and queues nothing. `renderItem` and middleware see the new `data` mid-drag.
   3. Anything else replaces `pending.layout` and `pending.itemIds`. Only the latest controlled layout is pending: a newer one replaces an older one.
4. **`setConfig`** replaces `pending.config`.
5. **Flush**, on `stop` and `cancel`, in this order:
   1. Commit the interaction result: the stop pipeline's result, or the cancel target.
   2. Apply `pending.config` as an idle `setConfig`. It emits `RGL_W003` only under the config rule above (cols, `maxRows` or the compactor key changed).
   3. If `pending.layout` is `sameInput`-equal, by id, to any layout in `active.produced`, it is a lagging echo of this interaction, and the committed result wins: drop it. Otherwise apply it as an idle `syncProps`. If it changes geometry against the committed result, emit `RGL_W003` with the item ids.
   4. Compare once against `lastNotifiedLayout` with `sameGeometry`, and emit at most one `layoutChange`.

**The echo contract.** A controlled layout that arrives during an interaction and equals, by id, a layout the engine produced during that interaction is treated as an echo, never as an instruction. A parent that wants to override the gesture result, for example after a server rejects the drop cell, sets its layout after `onDragStop`; an idle sync always wins. A debounced echo that lands after stop is such an idle sync, so it wins too and can move the item back to an earlier cell, as a late prop update does today. RGL-23 pins both cases with reducer tests, and the docs (RGL-41) state the contract.

**Batching is a test, not an assumption.** RGL-24 adds a scenario where a controlled parent sets its layout from `onDrag`'s argument 1, on a layout where compaction moves another item, and two pointer moves land inside one `act()`, so the parent renders once for two moves. The echo arrives one step late. The test asserts that the committed layout is the drop cell, that `onLayoutChange` fires once and that `RGL_W003` does not fire. A variant has the parent keep its layout sorted by `i`, so the echo arrives in a different order and still matches by id. It runs in the React 18 and 19 cells.

### Comparisons

Two comparisons with different jobs:

```ts
// src/core/engine/compare.ts
type Match = "index" | "id"; // default "index"
/** Notification: geometry and flags. Ignores `data`. */
export function sameGeometry(a: Layout, b: Layout, match?: Match): boolean;
/** Sync and echo: sameGeometry plus `data` by reference. */
export function sameInput(a: Layout, b: Layout, match?: Match): boolean;
```

`sameGeometry(a, b)` holds when:

- `a` and `b` have the same length and the same `i` at each index. With `match: "id"`, they hold the same set of ids instead, and each item is compared with the item of the same `i` through an id map;
- per item, the own keys other than `data` are the same set (`Object.prototype.hasOwnProperty.call` on both sides, so a key present as `undefined` differs from a missing key). `Object.hasOwn` is ES2022 and the repo compiles against the ES2020 `lib` (`tsconfig.json:4,39`);
- each value matches by SameValueZero (`x === y || (x !== x && y !== y)`);
- array-valued keys (`resizeHandles`, `constraints`) have the same length, and each element matches by SameValueZero.

SameValueZero, not `Object.is`, because that is what `fast-equals` does today. Measured in this revision with the installed `fast-equals` 4.0.3 (package.json:109): `deepEqual({x:0},{x:-0})` and `deepEqual({x:NaN},{x:NaN})` are both `true`, while `Object.is(0, -0)` is `false`.

`sameInput(a, b)` is `sameGeometry(a, b)` plus, per item, the same presence of `data` and `Object.is` on its value.

The echo rules and the data-only rule (queue rules 3 and 5) pass `match: "id"`, so a consumer that keeps its layout in its own order still produces echoes that match. Every other use compares by index, as `deepEqual` does.

| Use                                          | Comparison                         | Replaces                                                                                                                   |
| -------------------------------------------- | ---------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| Commit boundary against `lastNotifiedLayout` | `sameGeometry`                     | `deepEqual` in the mount effect (`GridLayout.tsx:441-449`), the notify effect (`:491-514`) and the stop paths (`:625,799`) |
| Binding gate before `syncProps`              | `sameInput`                        | the sync checks (`GridLayout.tsx:456,471`)                                                                                 |
| Echo rules and the data-only rule            | `sameInput`, `sameGeometry`, by id | new                                                                                                                        |
| Responsive ingest gates, per breakpoint      | `sameInput`                        | `ResponsiveGridLayout.tsx:274`, `react/hooks/useResponsiveLayout.ts:273` (RGL-37)                                          |
| Responsive notification gate, per breakpoint | `sameGeometry`                     | `react/hooks/useResponsiveLayout.ts:281` (RGL-37)                                                                          |

A prop change that only replaces an item's `data` fails `sameInput`, so the binding dispatches `syncProps` and the new reference reaches state, middleware and `renderItem`. It passes `sameGeometry`, so `onLayoutChange` does not fire. Mid-interaction, queue rule 3 patches the new `data` onto every engine layout at once, so `renderItem` sees it mid-drag and nothing waits in `pending`. Inline `data` objects therefore cannot cause a notify loop.

**RX-17 stays byte-identical.** `deepEqual` reports `{moved: false}` and `{}` as unequal because the key sets differ, and `sameGeometry` checks key sets the same way. It matches `deepEqual` on `0` versus `-0` and on `NaN`. Two differences remain by design: `data` is ignored, and constraint elements compare by reference. Factory constraints such as `aspectRatio()` already return a new object with new methods per call (`core/constraints.ts:234-242`), so `deepEqual` sees those as unequal too. A differential test runs `sameGeometry(a, b) === deepEqual(a, b)` over the golden corpus, its JSON round trips and the RX-17 fixtures, for every layout without `data`, with only the constraint-object exception. It is RX-19 in §7. The differential includes the N-7 fixture from round 2: an item whose `constraints` is an inline literal `[{ name, constrainPosition: f }]` rebuilt each render around a module-level `f`. `deepEqual` calls two of those equal and `sameGeometry` does not, so an idle `syncProps` commits each time. The docs say to create constraint objects once, as for middleware.

RX-5 (double fire) is fixed in 2.4.0 already, in place (RGL-15). The engine keeps the fixed behavior.

### Store binding

```ts
// src/react/state/store.ts

  getSnapshot(): GridEngineState;
  getServerSnapshot(): GridEngineState; // the initial state

  initial: { state: GridEngineState; events: readonly GridEvent[] },

  store: GridStore,
  selector: (s: GridEngineState) => T,
  isEqual?: (a: T, b: T) => boolean

```

- **Lifecycle.** The store lives in a ref, created once per mounted component on first render. It is never disposed or replaced. `subscribe` and `getSnapshot` are stable functions that read the store through the ref at call time. `useSyncExternalStore` owns the subscription: StrictMode's effect replay unsubscribes and resubscribes to the same store, with no render in between and nothing to recreate. On a real unmount the ref and the store are dropped together, and no callbacks fire. Timers and rAF loops belong to `GridItem` and binding effects, which clear them in their own cleanup.
- **Mount events.** `initial.events` holds the mount `layoutChange`, if any. The mount effect emits them once and sets a flag on the store. A replayed mount effect finds the flag set and emits nothing.
- **Callbacks.** `emit` reads the consumer's callbacks through a latest-value ref (`useLatest`), so inline callbacks work.
- **Selectors.** `GridLayout` selects the committed or working layout plus the placeholder, compared by reference. A same-cell move keeps both references, so it causes 0 `GridLayout` renders (T7).
- **Live pixels stay local.** The active item's pixel box is not in the store. It stays in the active `GridItem`, the mechanism #2304 added: a local revision counter re-renders only that item between snapped steps (`GridItem.tsx:251,553`).
- **Initial state** comes from `createInitialState`, synchronously, so the first render and `renderToString` show the synced, compacted layout.
- **Dispatch timing.** `syncProps` and `setConfig` dispatch from a layout effect, never during render. `emit` runs after the reducer returns, so a parent `setState` inside `onLayoutChange` never runs during render.
- **Test.** A StrictMode mount followed at once by a drag, with no parent rerender: each callback fires once, and `onLayoutChange` fires once at stop.
- **React floor.** The shim makes the binding work on React 16.8 and 17. The peer range moves to `>= 16.8.0` in 2.4.0 (RGL-08), and the shim dependency arrives with the store (RGL-24). It is a `dependency` and joins the tsup `external` list (`tsup.config.ts:17-24`), so the build never bundles a second copy.

### What the binding does

The binding is the only place that sees DOM events, elements and pixels.

1. **Pointer to grid.** On each pointer or scroll frame, it computes the grid-unit proposal from the client point (`getClientPoint`), the grid's client rect, its scroll offsets, the grab offset recorded at start and the transform scale. That is the input set `dropMath.ts` already uses for drops (`react/components/dropMath.ts:112-116`). Because the binding recomputes the proposal on every scrolled frame, edge scroll moves the item while the pointer holds still (RX-10d).
2. **Custom position strategies.** At drag start, when `positionStrategy.calcDragPosition` exists, the binding calls it with today's arguments: the client point and the pointer's offset inside the item. It converts the result as today: minus the parent rect divided by the scale, plus the parent scroll (`GridItem.tsx:402-418`). Each move adds the client-point delta since start, divided by the scale, to that start position. That is the sum RD's `deltaX`/`deltaY` give today, so mouse traces stay byte-identical. The existing call assertion stays (`test/spec/lifecycle-test.js:2465`), and a Playwright scenario drives the README's rotated strategy (`README.md:1028-1029`) and pins its per-frame boxes.
3. **Activation.** It runs the activation rule (§4, rank 8) before it dispatches `start`. Nothing reaches the reducer until the rule says "activate".
4. **Start.** It measures the container height once when `isBounded` and sends it on `start` (T9). If `dispatch` returns no `start` event (another interaction is active, the permission check failed, or middleware vetoed), the gesture goes to ignore-until-release.
5. **Ignore until release.** When the engine rejects a start or ends an interaction the gesture still holds (cancel, `itemRemoved`), the binding marks that item's RD or RR instance "ignore until release". Its handlers return early, and the item drops the `react-draggable-dragging` class and resets its local pixel box to the committed cell. The state clears on the first of: the adapter's next stop; `pointerup`, `pointercancel` or `blur` on `window`; or 30 s. The `window` listeners clear it on a deferred tick (`setTimeout(0)`) after the event, because pointer events dispatch before the compatibility `mouseup` that RD's capture-phase document listener turns into a stop (RD `DraggableCore.tsx:378-379`). A stop for which the binding holds no live id is dropped without a dispatch, so a release after a cancel never logs `RGL_W011`. This needs no upstream change, so it works on the RD 4.5.0 floor.
6. **Callbacks.** It maps each `interaction` event onto today's positional callbacks. It joins in the DOM values the reducer never sees: argument 5 is the last native event the binding saw for that gesture (a `KeyboardEvent` for a nudge, which fits `event: Event` at `core/types.ts:232`), argument 6 is the item node (`GridLayout.tsx:617` passes `data.node` today), and argument 7 is the `InteractionDetail`. For `kind: "drop"`, start and move events map to `onDragStart` and `onDrag` for the placeholder, as the faked `DraggableData` produces today (`GridItem.tsx:783-837`); a committed drop maps to `onDrop`; a cancelled drop maps to `onDragStop` with `detail.cancelled` and no `onDrop`.
7. **Errors.** It routes `error` events to `onError` when passed, and to `console.error` once per source and grid otherwise, in production too (§4, rank 4; §15).
8. On release, `GridLayout` dispatches `stop{interactionId}` without `to`. The reducer re-runs the pipeline on `lastProposal`, the last accepted proposal, so a release after a rejected move commits the last accepted step instead of re-running the rejected proposal at `phase: "stop"`, where a middleware `false` would cancel the whole drag.
9. A dedicated layout effect with empty deps dispatches `cancel("pointercancel")` when it re-runs and finds `active` set. It re-runs only when a hidden subtree is shown again (Suspense, `<Activity mode="hidden">`) and on a StrictMode replay, where `active` is `null`. The config and props effect never dispatches this cancel, because it re-runs on every controlled echo. The only cancel it dispatches is the `interactionKey` one below, and only when the key changed.

### The responsive cancel channel

The store is internal to `GridLayout`, so `ResponsiveGridLayout` cannot dispatch into it. `GridLayout` takes one new optional prop for this, `interactionKey?: string | number`. In the layout effect that dispatches config and props, the binding compares `interactionKey` first. When it changed while an interaction is active, the binding dispatches `cancel{reason: "breakpointChange"}`, and only then `setConfig` and `syncProps`. So the drag never continues under the new column count.

`ResponsiveGridLayout` passes its current breakpoint as the key. The prop exists for breakpoint changes, which is why its cancel reason is `"breakpointChange"`, and its docs say so. A consumer who composes `useResponsiveLayout` with `GridLayout` passes `interactionKey={breakpoint}` and gets the same behavior. Without the key, a breakpoint change mid-drag queues like any other prop change.

Order, from the code: `ResponsiveGridLayout` fires `onBreakpointChange`, `onLayoutChange` and `onWidthChange` in a passive effect that also sets its state (`ResponsiveGridLayout.tsx:329,399,416`). `GridLayout` sees the new key on the next render. So the cancelled `onDragStop` comes after those three callbacks. RGL-24 pins this order with a test. Its argument 1 is therefore the old breakpoint's layout, and the docs say that argument 1 of a cancelled stop is not a layout to persist (RGL-41).

### The boundary to react-draggable and react-resizable

Today `GridItem` talks to both libraries directly (`GridItem.tsx:898-932`) and works around them in four places:

- It prefixes `cancel` with `.react-resizable-handle` so handles do not start a drag (`GridItem.tsx:925`).
- It casts native events to `MouseEvent`. That hides the touch bug RX-7 (`GridItem.tsx:405-411,440-444`).
- It fakes `DraggableData` to simulate a drag for external drops (`GridItem.tsx:783-837`).
- It reads `nativeEvent ?? e` to work around the event type (`GridItem.tsx:717`, #2264).

  2.5.0 replaces these with **internal translation functions**, not interfaces. There is one implementation of each, so an interface would be a pass-through. Interfaces come with the pointer-events experiment (Later), once a second implementation exists.

```ts
// src/react/gesture/pointer.ts
export function getClientPoint(
  e: MouseEvent | TouchEvent,
  touchId?: number
): { clientX: number; clientY: number } | null;

// src/react/gesture/fromDraggable.ts
export function dragProposal(
  point: { clientX: number; clientY: number },
  frame: GridFrame // rect, scroll, grab offset, scale, PositionParams
): DragProposal;

// src/react/gesture/fromResizable.ts
export function resizeProposal(
  handle: ResizeHandleAxis,
  point: { clientX: number; clientY: number },
  frame: GridFrame
): ResizeProposal;
```

Rules at the boundary:

1. **RGL computes sizes from client coordinates.** It does not use react-resizable's `size`. Today the two models overlap: RR keeps `lastSize`/`slack`/`lastHandleRect` and corrects w/n handles through `getBoundingClientRect` on the handle (`Resizable.tsx:23-32,103-118`), while RGL recomputes left and top itself through `resizeItemInDirection` (rgl-react §6.2). RR stays for handle rendering and gesture capture.
2. The selector that keeps resize handles from starting a drag stays a local constant beside its one use. It is not exported.
3. **External drop and keyboard dispatch engine actions directly.** Nothing fakes `DraggableData`.
4. **Contract tests** (RGL-05) pin what the translation functions read from RD and RR, as structural subsets, so additive upstream fields do not break the floor-versus-latest cells (§8).

### 2. `Compactor.resolveDrag`

**Gap.** `moveElement` runs before the compactor and switches on `compactType` (`core/layout.ts:296-301,383-384,436`). A compactor that wants swap or insert-reorder semantics during a drag cannot get them (rgl-core X1). In #2213 a user reports that `onMove` on a custom compactor is never called (pluggability §2).

```ts
export interface DragContext {
  readonly layout: Layout; // working layout before this step
  readonly item: LayoutItem; // the moving item, as in ctx.layout
  readonly x: number; // target, after constraints and onProposal
  readonly y: number;
  readonly phase: InteractionPhase;
  readonly kind: "drag" | "drop"; // resize never comes here
  readonly source: InteractionSource; // "keyboard" for nudges
  readonly cols: number;
  readonly maxRows: number;
  readonly preventCollision: boolean;
  readonly allowOverlap: boolean;
  readonly startItem: LayoutItem;
  readonly startLayout: Layout;
}

export interface Compactor {
  readonly type: CompactType; // closed; resolveDrag is the extension point
  readonly allowOverlap: boolean;
  readonly preventCollision?: boolean;
  compact(layout: Layout, cols: number, ctx?: CompactContext): Layout;
  /**
   * Resolve collisions when ctx.item moves to (x, y). Must not mutate.
   * Return null to reject the step.
   */
  resolveDrag?(ctx: DragContext): Layout | null;
}

export type DragAxis = "x" | "y" | null; // null: free-form swap
export function classicResolveDrag(
  ctx: DragContext,
  axis: DragAxis,
  opts?: { readonly order?: "rowCol" | "colRow" } // default from axis
): Layout | null;
```

- **Default.** Each built-in compactor sets `resolveDrag` explicitly, through the same helper a third party would call. `verticalCompactor` and `fastVerticalCompactor` use `ctx => classicResolveDrag(ctx, "y")`. `horizontalCompactor` and `fastHorizontalCompactor` use `"x"`. `noCompactor` uses `ctx => classicResolveDrag(ctx, null)`, the free-form swap; it does not return `null`. Each overlap variant uses the axis of its base type. `wrapCompactor` uses `classicResolveDrag(ctx, "x", { order: "rowCol" })`, because wrap sorts row-col (`core/sort.ts:32-34`) but pushes horizontally (`core/layout.ts:383`). These reproduce today's `moveElement` cascade on a working copy the helper owns. `moveElement` stays exported as a wrapper (§12).
- **No `resolveDrag`.** A compactor written for 2.0-2.3 has none. The engine then picks the helper from `type`, as `moveElement` does today: `"vertical"` gives `"y"`, `"horizontal"` gives `"x"`, `"wrap"` gives `"x"` with `order: "rowCol"` (the call `wrapCompactor` makes, since `moveElement` pushes wrap horizontally, `core/layout.ts:383`), and `null` gives `null`. RGL-35 adds a fixture for a 2.3-style custom `{ type: "wrap", compact }` compactor.
- **Reject is explicit.** `null` means "reject this step". It is not inferred from an unchanged layout, because a normal stop in the same cell also returns an unchanged layout. On a move, `null` drops the step. On a stop, the last accepted working layout commits, as `preventCollision` behaves today (`core/layout.ts:317-322`).
- **Resize never calls `resolveDrag`.** Resize runs `resizeElement` instead (§3 pipeline). A swap compactor therefore cannot turn a resize into a swap.
- **Composition.** The output goes to `compact`.
- **Test in isolation.** Pure Jest: `resolveDrag(ctx)` against golden fixtures. `extras/swapCompactor.ts` ships with its own spec, as executable documentation, the way `wrapCompactor` does today.
- **Name.** No `onMove` field exists in `src/`, the README or the examples today (grep). There is no existing name to alias.
- `type` stays the closed `CompactType` union (`core/types.ts:211`). A third party that wants different drag semantics picks the existing `CompactType` closest to its compaction and supplies `resolveDrag`; the engine never reads `type` to resolve a drag when `resolveDrag` is set. `PositionStrategy.type` stays closed too; its only reader is `GridLayout.tsx:388`.
- RGL-35 exports `classicResolveDrag` and the `DragContext` and `CompactContext` types from `src/core/index.ts`, next to the existing helpers for custom compactors (`core/index.ts:130-133`), and `swapCompactor` from `src/extras/index.ts`. A consumer fixture compiled against the built package imports each of them.
- **Change detection.** A compactor change is detected by comparing `type`, `allowOverlap`, `preventCollision` and the `compact` reference, not object identity (RGL-17, 2.4.0). From RGL-35 the `resolveDrag` reference joins the key (§3 config equality). An inline `{...verticalCompactor, preventCollision: true}` rebuilt every render is therefore not a change, while a swap to `fastVerticalCompactor` or to a different `resolveDrag` is (fixes RX-8b). `getCompactor` keeps returning a new object per call when `preventCollision` is set (`core/compactors.ts:349-351`); the comparison makes a cache unnecessary, and a shared object would let one caller's mutation reach another.

### 4. Interaction middleware

**Gap.** Callbacks only observe. There is no veto and no transform, and the pre-compaction layout is never exposed (pluggability §1; #345). The fix also covers cancel or revert on stop (#1966) and mutation in stop (#1979).

```ts
export type DragEdit = { readonly x?: number; readonly y?: number };
export type ResizeEdit = { readonly w?: number; readonly h?: number };
export type ProposalResult = void | false | DragEdit | ResizeEdit;
export type ResolvedResult = void | false | Layout;

export interface InteractionMiddleware {
  readonly name: string; // used in errors, warnings and rejectedBy
  /** After constraints. start, move and stop. */
  onProposal?(d: InteractionDetail): ProposalResult;
  /** After compaction. move and stop. */
  onResolved?(d: InteractionDetail): ResolvedResult;
}

// GridLayout and useGridLayout props:
//   middleware?: readonly InteractionMiddleware[]
//   onError?: (error: unknown, source: string, detail?: InteractionDetail)
//     => void
```

Both results are bare values: an edit object, or a `Layout` array. `false` vetoes, `undefined` passes.

- **`onProposal`** runs after constraints, at `start`, `move` and `stop`. At `start`, `d.proposed` is the start item. At a drag or resize `start` only a `false` veto counts: no step runs there, so a returned edit is ignored with the dev warning `RGL_W012`. A drop start runs a step, so its edit applies. A drag or drop edit may set `x` and `y`; a resize edit may set `w` and `h`. Any other field is ignored, with warning `RGL_W005`. An edit is validated first (finite, rounded to integers, inside the §14 bounds), then the constraints run again, then validation runs once more. So middleware cannot hand a fractional or non-finite value to a compactor, the input that makes `fastHorizontalCompactor` throw (C-B4). For `n` and `w` handles, `x` and `y` are re-anchored after every size change, so the opposite edge stays fixed.
- **`onResolved`** runs after compaction, at `move` and `stop`. A returned layout is validated (same id set, finite integers, inside bounds) and used without a second compaction. An invalid result emits warning `RGL_W005`, in production too, and counts as a veto for that step.
- **Composition.** Array order. The first `false` stops the chain and vetoes the step. A returned edit or layout feeds the next middleware. Middleware runs after constraints, so constraints stay the place for geometric clamping (RFC 0002).
- **Veto semantics per phase.**
  - `start`: no interaction begins. `active` stays `null`. No `onDragStart` fires. The binding ignores the gesture until release.
  - `move`: the step is dropped. State stays at the last accepted step.
  - `stop`: cancel semantics (below), with `cancelReason: "vetoed"`. That reverts the whole drag, unlike a `null` from `resolveDrag`. The docs (RGL-41) carry a recipe for a forbidden-zone middleware that keeps the item at its last valid position on release: at `stop`, return an edit back to the item's cell in `d.layoutBefore` instead of `false`.
- **Errors.** A throw from middleware, `resolveDrag` or `compact` is caught by the reducer and returned as an `error` event. The binding calls `onError` if passed. Without `onError`, it calls `console.error` once per source and grid, in production too, with the strategy name and phase; a throwing strategy is a third-party bug, and swallowing it silently leaves an item that will not move. Inside an interaction the step counts as a veto, and at `stop` that means cancel semantics with `cancelReason: "error"`. Outside an interaction (phase `"sync"`: initial state, `syncProps`, `setConfig`, `setLayout`) the previous state is kept (§3). Nothing is rethrown.
- **Start/stop pairing.** Every `onDragStart` and `onResizeStart` gets exactly one matching stop callback. A cancel or a stop veto fires `onDragStop`/`onResizeStop` with `(startLayout, startItem, startItem, null, e, el, detail)`, where `detail.cancelled` is `true` and `detail.cancelReason` says why. There is no separate cancel callback: argument 7 carries the whole story. Consumers that ignore it see a no-op drag that ends where it started. `startLayout` never contains an item removed mid-interaction (§3 queue rules 1 and 2). Only unmounting the grid skips callbacks. The docs say that argument 1 of a cancelled stop is not a layout to persist; after a `breakpointChange` cancel it is the old breakpoint's layout (§3). The external-drop placeholder follows the same rule on cancel: leaving the grid fires `onDragStop` with `cancelReason: "dropLeft"`, which closes half of RX-11a. A committed drop still ends with `onDrop` and no `onDragStop` until v3 (open question 6).
- **Callback detail.** Every existing callback gets an optional seventh argument, the `InteractionDetail` for that step. Positional arguments 1-6 keep today's values. This answers #345 without changing a signature.
- **Test.** Pure engine tests: a vetoing middleware leaves `state.layout` unchanged; a replacing middleware's layout is committed without a second compaction; an edit with `x: 1.5` is rounded and clamped; a resize edit's `x` is ignored with `RGL_W005`; an edit returned at a drag `start` is ignored with `RGL_W012`; a throw becomes an `error` event, at `move`, at `stop` and at `"sync"`. RTL tests confirm the seventh argument reaches `onDragStop`, and that a throw without `onError` logs once under `NODE_ENV=production`.

### 5. `LayoutItem.data` passthrough

**Gap.** `cloneLayoutItem` copies a fixed list of 16 keys, so custom fields vanish on every compaction (`core/layout.ts:81-99`, verified with `data`; rgl-core §1.2). In #929 the maintainer's answer was "store a map elsewhere" (pluggability §2).

```ts
export interface LayoutItem<TData = unknown> {
  // ...existing fields
  readonly data?: TData;
}
export type Layout<TData = unknown> = readonly LayoutItem<TData>[];
// The parameter is threaded through every type that carries a layout:
// GridLayoutProps<TData>, GridLayout<TData>, EventCallback<TData>,
// ResponsiveGridLayoutProps<B, TData>, ResponsiveLayouts<B, TData>,
// useGridLayout<TData>, useResponsiveLayout<B, TData>.
```

- **Default.** `cloneLayoutItem` copies `data` **by reference** and adds no other keys. Items without `data` keep their exact 16-key shape. That matters because `fast-equals.deepEqual({minW: undefined}, {})` is `false` (rgl-core §1.0). `Layout` is already a readonly array today (`core/types.ts:113`), so the generic adds no readonly change.
- **Sync and notification.** `sameInput` compares `data` by reference, so a data-only prop change reaches state. `sameGeometry` ignores it, so that change fires no `onLayoutChange` (§3). The responsive `deepEqual` paths move in the same PR, compared per breakpoint: the ingest gates (`ResponsiveGridLayout.tsx:274`, `useResponsiveLayout.ts:273`) to `sameInput`, and the notification gate (`useResponsiveLayout.ts:281`) to `sameGeometry`. None of them walks `data`.
- **Generic callbacks.** `onLayoutChange?: (layout: Layout) => void` (`GridLayout.tsx:158`) is a function-typed property, so a `(l: Layout<MyData>) => void` handler fails under `strictFunctionTypes` unless the props are generic. The same holds for every `EventCallback` and the responsive and hook types, which is why the parameter is threaded through all of them.
- **Composition.** Opaque to every strategy. Middleware and `renderItem` can read it.
- **Test.** Pure: `cloneLayoutItem`, `compact`, `resolveDrag` and `sync` keep `data` by reference. Consumer compile fixtures pass a `Layout<MyData>` handler to `onLayoutChange`, `onDragStop` and the responsive `onLayoutChange` (§11). RTL: a data-only prop change reaches `renderItem` on `GridLayout`, `ResponsiveGridLayout` and `useResponsiveLayout`, idle and mid-drag, with no `onLayoutChange`. The hook cases run through its props and through both setters, with a cyclic `data` object.

### 7. `renderItem`

**Gap.** The child contract (forward the ref, `style`, `className`, mouse and touch handlers, render `{children}`) is the largest support load (#1241, #299). #506 asks for the computed size in children.

```ts
export interface ItemRenderState {
  readonly item: LayoutItem;
  readonly position: Position;
  readonly state: "idle" | "dragging" | "resizing" | "dropping";
}
// GridLayout prop:
//   renderItem?: (child: React.ReactElement, s: ItemRenderState)
//     => React.ReactNode;
```

- **Default.** With `renderItem` unset, the current child contract applies unchanged.
- **Where it runs.** `GridLayout` calls `renderItem(child, state)` during its own render, for every item, and passes the result as `GridItem`'s children. RGL renders its own wrapper `<div>` with the position style, classes, handlers and resize handles. The user's content needs no ref forwarding. That is the #346 goal of "always renders a `<div>` so styles are settable", opt-in.
- **`className` and `style`.** The wrapper's class is RGL's classes plus `child.props.className`. Its style is `{...child.props.style, ...positionStyle}`, so RGL's position keys win. `renderItem` receives the child with `className` and `style` removed, because they moved to the wrapper.
- **No cache.** There is no per-item element cache. A cache keyed on anything less than every input `renderItem` reads would show stale content, and `position` alone changes with every width change. A new element per render means `GridItem` re-renders whenever `GridLayout` renders with `renderItem` set. `GridLayout` itself renders only on a layout or placeholder change (T7) or a parent render. Consumers who need fewer renders memoize the content component (`React.memo`) or the function. T8 is measured on grids without `renderItem`.
- **Position during a gesture.** `position` is the cell-snapped box. The live sub-cell box of the active item stays local to `GridItem` (§3).
- **Composition.** A transition library can wrap items through `renderItem` (rank 12).
- **Test.** RTL: a spy `renderItem` receives `state: "dragging"` mid-drag; a plain function component (no forwardRef) works as content; a width change passes the new `position`; a closed-over parent value that changes shows up in idle items on the next render. Pure: the `ItemRenderState` derivation is a selector over engine state.

### 8. Activation rules

**Gap.** `dragConfig.threshold` covers distance only (`core/types.ts:498`). RGL reimplements the threshold FSM inside `GridItem` (`GridItem.tsx:437-448,492-527`), and on touch the FSM is skipped entirely because `clientX` is undefined (RX-7). PR #1607 (`delayedDragOnTouch`, 26 comments) and RD #350 (25 comments) ask for delay.

```ts
export type ActivationRule =
  | { readonly distance: number }
  | { readonly delay: number; readonly tolerance: number };

export interface DragConfig {
  // ...existing fields; `threshold` stays and maps to { distance }
  readonly activation?:
    | ActivationRule
    | { readonly mouse?: ActivationRule; readonly touch?: ActivationRule };
}

// core/interaction/activation.ts: numbers in, no DOM types
export function decideActivation(
  rule: ActivationRule,
  dx: number,
  dy: number,
  elapsedMs: number
): "activate" | "wait" | "cancel";
```

- **Data only.** There is no predicate function in 2.5.0. A rule is `{distance}` or `{delay, tolerance}`.
- **Where it runs.** In the binding, before `start` is dispatched. Nothing reaches the reducer until the rule says `activate`. A pure click therefore never adds the `react-draggable-dragging` class (`GridItem.tsx:447`).
- **Default.** `{ distance: threshold }` (3 in v2, 0 in legacy). The default path is unchanged: a distance of 0 activates on the start sample itself, as `if (dragThreshold > 0)` does today (`GridItem.tsx:439`), and the comparison keeps today's `distance < dragThreshold` wait (`GridItem.tsx:498`).
- **Delay.** A timer starts at pointer-down and calls `decideActivation` with the current offset when it fires, so a stationary long-press activates without a move event. Moving past `tolerance` before the timer cancels the rule.
- **Touch delay and native scroll.** `preventDefault` only works when called synchronously while the browser dispatches a cancelable event. A timer callback cannot call it. With a delay rule on touch, the binding passes `allowMobileScroll` to RD, so RD does not call `preventDefault` on `touchstart` (installed RD 4.5.0, `node_modules/react-draggable/build/cjs/DraggableCore.js:105`). The binding adds its own non-passive `touchmove` listener. It calls `preventDefault` there while the delay is pending and the finger is within `tolerance`, and on every `touchmove` after activation. Once the finger passes `tolerance`, the listener stops calling it and the rule cancels. A browser may decide scroll ownership on the first `touchmove`, so a cancelled delay can still lose native scroll for that one touch; the verification below records which.
- **Verification.** Automation cannot cover this check. Script-dispatched touch events are untrusted and never scroll, and CDP `Input.dispatchTouchEvent` does not fire DOM touch events in headless Chromium, as the repo already records (`test/e2e/touch-drop.spec.ts:30-31`). So the native-scroll behavior is checked by hand on iOS Safari and Android Chrome in the 2.5.0 rc window, as a line in the rc checklist (§15). Jest with fake timers covers the listener logic.
- **Veto after activation.** If middleware vetoes the `start` that activation dispatched, RD's start callback has already returned (`DraggableCore.js:128` checks `false` only during that call). The binding ends the gesture through the ignore-until-release state. No consumer stop fires, because no start fired.
- **Sub-threshold deltas.** On activation, the binding replays the full delta from the start sample. Today those deltas are discarded, so the item lags the pointer by up to `threshold` px (rgl-react §4.12). Listed as RX-12.
- **Test.** Pure `decideActivation` tests with fake times. jsdom tests with fake timers for a touch long-press and for `preventDefault` calls on `touchmove` within and past `tolerance`. The manual device check above.

### 9. Keyboard

**Gap.** Nothing exists (pluggability §1). Asked for in #1907, #936, #1795 and in #346 by tambaqui.

```ts
// The GridAction member (§3):
//   { type: "nudge"; itemId: string; delta: NudgeDelta }
// The reducer's nudge step lives in core/engine/reduce.ts (internal).

// GridLayout prop:
//   keyboard?: boolean | {
//     moveKeys?: Partial<Record<string, readonly [number, number]>>;
//     resizeModifier?: "shift" | "alt";
//     cancelOnEscape?: boolean; // default true when keyboard is on
//     announce?: (message: string) => void;
//   }
```

- **Default.** Off. With `keyboard: true`, arrow keys move the focused item and shift plus arrows resize it.
- **One mechanism.** A key press dispatches one `nudge` action. The reducer checks movability, then runs start, one step and stop through the same pipeline as a pointer: a move nudge goes through `resolveDrag`, a resize nudge through `resizeElement`, both with constraints and middleware and `source: "keyboard"`. Keyboard and pointer moves cannot diverge. There is no batch API.
- **During a pointer interaction.** A `nudge` is a no-op while `active` is set (§3), so a key press cannot move or stop someone else's drag.
- **Commit.** Each key press commits at once. A rejected press (the permission check, a veto, a `null` from `resolveDrag`, a throw) commits nothing and fires no callbacks (§3).
- **Callbacks.** A nudge fires the drag trio (`onDragStart`, `onDrag`, `onDragStop`) or the resize trio, with `detail.source: "keyboard"` and the `KeyboardEvent` as argument 5.
- **Where the handler lives.** With a roving `tabIndex`, focus sits on items, so the key handler is on each item wrapper. It ignores events whose `target !== currentTarget` or that are `defaultPrevented`, so arrow keys in an `<input>` inside an item never move it.
- **Escape.** Escape cancels an active pointer interaction only when `keyboard` is on (`cancelOnEscape`). It is never on by default. Focus can be on `body` during a mouse drag, so the binding listens for Escape on the document while an interaction is active.
- **Accessibility.** One tab stop for the grid, with a roving `tabIndex` across items. Each item gets `aria-describedby` pointing at instructions. Moves are announced through a live region, written with `textContent`. There is no `aria-grabbed`, which WAI-ARIA 1.1 deprecated.
- **Not exported in 2.5.0.** A `useGridKeyboard` hook would need the store, which stays internal. It waits for the public store (rank 14).
- **Test.** Pure reducer matrix for `nudge`: bounds, statics, both permission override directions, collisions, `preventCollision`, a rejected nudge that emits no interaction events, and a nudge while a drag is active. RTL with `@testing-library/user-event` (a new dev dependency): assert `onLayoutChange`, the announce text, and that an arrow key inside an `<input>` does nothing.

## 5. Performance Plan

### Measured baselines

**Core, per operation** (rgl-core §3.1: Node 24, Apple Silicon, `bench.cjs`). The generator mixes sizes from 1x1 to 3x3 with +-1 row jitter, then pre-compacts. A "drag frame" moves item 0 to the middle row. Treat the ms values as orders of magnitude. The n=50 row includes JIT warmup noise.

| n    | `moveElement` only | drag frame (move + `verticalCompactor`) | drag frame (move + `fastVerticalCompactor`) | `verticalCompactor.compact` | `horizontalCompactor.compact` |
| ---- | ------------------ | --------------------------------------- | ------------------------------------------- | --------------------------- | ----------------------------- |
| 50   | 0.07 ms            | 1.2 ms                                  | 0.2 ms                                      | ~1 ms                       | 0.6 ms                        |
| 500  | **16 ms**          | **48 ms**                               | **22 ms**                                   | **51 ms**                   | 32 ms                         |
| 5000 | **8,480 ms**       | **20,100 ms**                           | **10,600 ms**                               | 3,300 ms                    | 3,390 ms                      |

These run about 10x above RFC 0001's baseline (vertical compaction at 500 items = 4.9 ms, move = about 7 us; `rfcs/0001:1494-1510`). That benchmark (`test/spec/benchmark-test.js:30-42`) uses a uniform 2x2 tiling, which never cascades. Mixed sizes trigger the recursive cascade. This RFC treats the mixed-size corpus as the realistic case.

**The columns do not add up, and are not meant to.** At n=500, `moveElement` only (16 ms) plus `verticalCompactor.compact` (51 ms) is 67 ms, but the drag frame is 48 ms. At n=5000, 8,480 + 3,300 = 11,780 ms, against a 20,100 ms frame. Each column is its own timing loop over different inputs:

- `verticalCompactor.compact` times `compact(base)` on the same uncloned, already-compacted `base` every repetition (`bench.cjs:13`). `compact` writes to its input in place (C-M1), but a check in this revision found `base` unchanged after one and two calls, so every repetition sees the same input.
- The drag frame times a fresh `cloneLayout(base)`, one `moveElement` and one `compact` of the moved layout (`bench.cjs:21`). "`moveElement` only" times the clone and the move without the compact (`bench.cjs:22`).
- Each loop runs one warmup call and then 20 repetitions at n=500, 3 at n=5000 (`bench.cjs:4,9`).

So the compact inside a drag frame runs on a different layout from the compact column. Why the totals differ by that much has not been measured. The millisecond columns stay informational. Targets are checked on op counts from the RGL-02 harness (#2323), which reproduces the count rows below exactly.

**Core, operation counts** (rgl-core §3.1, `count.cjs`):

| n    | `moveElement`, one drag frame                | `verticalCompactor`, already-compacted input                                |
| ---- | -------------------------------------------- | --------------------------------------------------------------------------- |
| 50   | 9 sorts, 9 filters                           | 46 `getStatics` filters, 50 `indexOf`, 45 `findIndex`                       |
| 500  | **180 sorts** (length sum 90k), 180 filters  | 496 filters (length sum 248k), 500 `indexOf` (250k), 495 `findIndex` (247k) |
| 2000 | **958 sorts** (length sum 1.9M), 958 filters | about 2000 of each, length sum about 4M each                                |

The figures in brackets are measured, but they are not elements scanned. `count.cjs` adds `this.length` on every call (`count.cjs:6`), so "250k" is 500 calls x a 500-item array. It is an upper bound for the scan. The scan itself is smaller. `layout.indexOf(sortedItem)` (`core/compactors.ts:200`) stops at the match, so on input whose order matches the sort order, finding item k takes k + 1 comparisons:

```
sum over k = 0..499 of (k + 1) = 500 x 501 / 2 = 125,250
```

That is a derived figure, under that ordering assumption. `findIndex` at `core/compactors.ts:50` has the same shape. RGL-10 (#2326) removes both calls, so their exact scan counts no longer matter.

**Where the O(n^2) terms come from:**

- `moveElement` re-sorts the full layout on every recursive call (`core/layout.ts:295`), copies it (`:325`) and scans all collisions (`:307`). That is O(k \* n log n) per mousemove, where k is the cascade depth (rgl-core §3.2, rank 1).
- Classic compactors call `resolveCompactionCollision` even on an already-compacted layout (495 of 500 items). Each call does a `findIndex` (`core/compactors.ts:50`) and a `getStatics` (`:53`), because `hasStatics` is not passed down from `:111` and `:149`. Restoring input order costs a `layout.indexOf` per item (`:200,239`; `extras/wrapCompactor.ts:87,118`) (rgl-core §3.2, ranks 2-3).
- `correctBounds` runs a static-collision loop that is O(dy \* n) per static (`core/layout.ts:230-232`). With S statics that overlap at the same cell and height h, that is about h x S^3 / 2 `collides` calls. The round-2 skeptic review measured 7, 24, 230 and 2,107 ms at S = 10, 20, 40 and 80 with h = 10,000. RGL-49 bounds it (§14).
- **The `collides` floor.** `compactItemVertical` moves each item up while `getFirstCollision(compareWith, l)` finds nothing, then resolves collisions until it finds nothing (`core/compactors.ts:104,110`). `getFirstCollision` scans the whole list when there is no collision (`core/collision.ts:44-50`), and `compareWith` grows by one item per placed item. So the final no-collision check alone costs at least:

  ```
  sum over k = 0..n-1 of k = n(n-1)/2
  n = 500:   500 x 499 / 2   =   124,750 collides calls
  n = 2000: 2000 x 1999 / 2  = 1,999,000 collides calls
  ```

  This is a lower bound from the code. #2323 measured 497,439 `collides` calls for one compaction at n=500 (`compact/mixed`). T1-T3 do not remove it (T14).

**React layer, per drag move** (rgl-react §2):

- `GridLayout` re-renders on every move, because `setActiveDrag(newObject)` and `setLayout(newArray)` always produce new references (`GridLayout.tsx:587-588`), even when the cell did not change.
- Memo defeats. An inline `gridConfig={{margin:[10,10]}}` re-renders every item. So do the legacy wrappers' destructured default `margin = [10,10]` (`legacy/ReactGridLayout.tsx:129`) and the v2 Responsive default (`ResponsiveGridLayout.tsx:212`): on an identical rerender, every item re-rendered (probe LG). `getCompactor(type, overlap, true)` returns a new object per call (`core/compactors.ts:349-351`). `createScaledStrategy(scale)` runs per legacy render (`legacy/ReactGridLayout.tsx:228`).
- Synchronous layout reads per move:
  - `offsetParent.clientHeight` when `isBounded` (`GridItem.tsx:539-540`)
  - the same read on every resize event (`GridItem.tsx:695`)
  - edge scroll `getBoundingClientRect` per rAF (`edgeScroll.ts:56`)
  - drop `getBoundingClientRect` per dragover (`dropMath.ts:78`)
- `processGridItem` is a `useCallback` with 27 dependencies, recreated every render (`GridLayout.tsx:1169-1269`).
- `deepEqual` compares `layout` at least 4 times after a drag stop (rgl-react §2.5).

### Benchmark harness

The op-count harness is RGL-02, merged as #2323. Its design, from that PR:

Wall-clock timing stays in the opt-in `yarn bench` (`test/jest.bench.cjs`).

## 6. Clarity Plan

### Rules

These rules apply to every file this RFC touches. Reviewers cite the rule number.

1. **One job per function.** `moveElement` today writes the position, sorts, queries collisions, applies the overlap and prevent policies and orchestrates the cascade through mutual recursion (rgl-core §4.3). After the split: `resolveDrag` orchestrates, `collisionPolicy` decides push vs swap vs probe, `cascade` moves colliders. `correctBounds` splits into three passes (horizontal fix, Infinity fix, static de-overlap) behind the same exported function.
2. **Axis abstraction for vertical and horizontal mirrors.** One descriptor:

   ```ts
   interface Axis {
     readonly pos: "x" | "y";
     readonly size: "w" | "h";
     readonly cross: "x" | "y";
     readonly crossSize: "w" | "h";
     compare(a: LayoutItem, b: LayoutItem): number;
   }
   ```

   `compactItemVertical`/`compactItemHorizontal` (`core/compactors.ts:90-164`) and `verticalCompactor`/`horizontalCompactor` (`:178-246`) become one classic compactor in `core/compaction/classic.ts`, driven by descriptors in `core/geometry/axis.ts` (RGL-10, #2326). The old names stay as exported wrappers.

3. **No `any`, no `as unknown as`, no casts that hide a type error.** Today `GridItem.tsx` has 9 `e as unknown as MouseEvent`/`Event` casts (`:405, 440, 468, 490, 522, 566, 629, 812, 831`). They hide RX-7. Other casts: `resizeHandle as ResizeHandle` (`GridLayout.tsx:1191`), `margin as [number, number]` (4 places), `rest as unknown as P` (`WidthProvider.tsx:129`), `Mutable<LayoutItem>` writes in `onResize` (`GridLayout.tsx:709-716,765`) (rgl-react §3.3). One `getClientPoint(e: MouseEvent | TouchEvent)` replaces the event casts. ESLint enforces `@typescript-eslint/no-explicit-any` and `no-unsafe-*` on `src/`.
4. **Guard clauses over nesting.** `compactHorizontalFast` has a 95-line loop body with 4 nesting levels (`extras/fastHorizontalCompactor.ts:154-227`). The cyclomatic-complexity lint already in the repo gets a per-function budget for `src/core`.
5. **Lookup tables over string lists and switch chains.** Resize handle behavior is spread over string lists in `GridLayout.tsx:674-685`, `:714` and `:762`, and 8 handlers in `resizeItemInDirection` (`core/position.ts:239`). One table:

   ```ts
   const HANDLE: Record<
     ResizeHandleAxis,
     {
       movesX: boolean;
       movesY: boolean;
       growsW: 1 | 0 | -1;
       growsH: 1 | 0 | -1;
     }
   >;
   ```

6. **Core functions that return a result never mutate their inputs.** The policy covers every function whose output is its return value: each compactor's `compact`, `moveElement`, `correctBounds` and every new function. They stop mutating in 2.4.0 (RGL-11, RGL-14). Their outputs stay byte-identical; only the golden `inputAfter` column changes. One changelog line covers it (§12). Every internal caller of `correctBounds` already reads its return value (`GridLayout.tsx:282`, `ResponsiveGridLayout.tsx:189`, `core/responsive.ts:149`, `react/hooks/useGridLayout.ts:169,199,356,390,429`), so that change needs no caller edits. The exported helpers that work by mutation, `resolveCompactionCollision` (returns `void`, `core/compactors.ts:38-44`, writes at `:75`) and `compactItemVertical`/`compactItemHorizontal`, keep their behavior in 2.x and get `@deprecated` in 2.5.0. RGL-49 bounds the work of `compactItemVertical` and `compactItemHorizontal` without changing that contract (§14). A custom compactor built on them keeps working. The classic compactor uses a pure internal helper that returns a new layout instead. That makes the `layout.ts:5` header "All functions treat layouts as immutable" true for the functions it describes (rgl-core §4.2). There is no wrapper that replays writes onto the caller's objects.
7. **One ref-mirror helper.** Render-phase ref writes (`GridLayout.tsx:407,424,438`, `GridItem.tsx:273,646-647`) are unsafe under concurrent rendering. All of them go through `useLatest`, which assigns in a layout effect (rgl-react §2.3).
8. **Names say what the code does.** For example, `preventCollision` inside `moveElementAwayFromCollision` means "collider is static" (`core/layout.ts:385`). `isUserAction` is reused as a "try once" flag (`:389`). `movingUp` is true for horizontal moves (`:296-301`) (rgl-core §4.2).
9. **Comments match the code.** Each wrong comment in rgl-core §4.2 and rgl-react §3.3 is fixed in the PR that touches its file. Examples: `GridItem.tsx:691-694` ("offsetParent is the grid container", false), `edgeScroll.ts:8-9` ("or the window", false), `extras/fastHorizontalCompactor.ts:83` (sort order), and the unreachable branch at `:205-208`.
10. **Core types are React-free.** No `React.*` in `src/core` (`core/types.ts:329,533-537`; `core/position.ts:271-314`). `calcStyle` returns `csstype`'s `Properties<string | number>`, which `React.CSSProperties` extends, so existing strategies stay assignable (§3). A lint rule bans `react` imports under `src/core`.
11. **Exported defaults keep their 2.3.0 types.** `defaultConstraints: LayoutConstraint[]` (`core/constraints.ts:384`) and the default config objects (`core/types.ts:468-592`) stay mutable in their types, because the sinks take mutable arrays (`core/constraints.ts:403-405`) and consumers may push onto them today. New code treats them as read-only by convention. Readonly types and freezing wait for v3. The RGL-46 compile fixtures pin this.
12. **Freeze inputs only in tests.** The golden and reducer suites deep-freeze inputs with `test/util/deepFreeze.js`. Dev builds never freeze, because a frozen object would reach consumer callbacks and throw on a write that works in production.

The lockfile pin is not the consumer pin. RGL's own tests and CI run RD 4.5.0. A consumer installing RGL today can resolve RD 4.7.2. So two things are true at once:

1. **The `^4.4.6` floor is wrong.** `allowMobileScroll` landed in 4.5.0 (`node_modules/react-draggable/CHANGELOG.md:3-10`), so a consumer pinned to 4.4.6 silently loses it (RX-18).
2. **The 4.6.0 ctrl+click change is probably already reaching RGL users.** Since 4.6.0, ctrl+left-drag no longer starts a drag on any OS (`DraggableCore.tsx:322`, commit `fb246a2`; draggable header table). RGL's tests have never run against it. Raising the floor does not decide this behavior. It needs its own line in the changelog and migration table (D-ctrl, open question 1).

What changed in RD between 4.5.0 and 4.7.2 (draggable header table): the ctrl+click change; `findDOMNode` no longer falls back when `nodeRef.current` is null (RGL always passes `nodeRef`); the TypeScript rewrite with ESM and an `exports` map; a `nonce` prop; type and bundler fixes.

What changed in RR from 3.2.0 to 4.0.2 (RR CHANGELOG): 4.0.0 is a types-only major (bundled TypeScript declarations, Flow shims removed). 4.0.1 changes `lockAspectRatio` to orthogonal projection. RGL does not use `lockAspectRatio` or `axis` (rgl-react §6.2). So moving to RR 4 should not change RGL behavior. The RGL contract tests and traces confirm this before the bump merges.

## 10. Failure Matrix

Columns: the state or input, what the operation does, how it can fail, and what the caller is told. "Caller" means the consumer's callbacks and console, not the engine's internal state. "Stop callback (cancelled)" is shorthand for `onDragStop`/`onResizeStop` with `(startLayout, startItem, startItem, null, e, el, detail)`, `detail.cancelled: true` and a `cancelReason` (§4, rank 4). `startLayout` there never contains an item removed during the interaction.

Rows marked **(today: pinned)** have a #2321 trace of today's behavior, which RGL-23 and RGL-24 list as an expected diff (§9 Phase 5). Rows marked **(2.4.0)** apply from 2.4.0. All other rows apply from 2.5.0.

## 11. Testing Strategy

Each layer below sits on the golden masters already decided. None of them replaces a golden.

### 1. Golden masters (decided, merged)

- **RGL core** (F1): every row of rgl-core §1.2, interaction scripts through `moveElement` + `compact`, and fast-vs-classic differentials, recorded as known divergences. The serializer keeps `undefined`, `±Infinity`, `NaN`, holes and order. It records `out` and `inputAfter` separately, plus reference identity (rgl-core §1.0).
- **RGL React** (RGL-03, #2321): `test/golden-react/`, jsdom traces for each scenario and variant, through real react-draggable and react-resizable handlers, with no mocks of either (rgl-tests §6b). Each step records callbacks, styles, classes, the placeholder and Profiler commit counts (`test/golden-react/README.md` on master).
- **Enforcement**: an ordinary run fails on any changed or missing fixture; only `GOLDEN_UPDATE=1` writes. The PR description explains each diff, and the template asks for it (RGL-45, §15).
- **RD and RR** (F2, F3): jsdom traces, one `act()` per event, with the fake layout engine for RR's w/n correction (resizable §7), plus browser cross-checks.

### 2. Invariants, scoped by operation and input domain

A careless `golden-update` cannot hide these (rgl-tests §6a). Each invariant names the operations and inputs it covers. A case outside that domain is a plain golden fixture, so behavior pinned in §7 is not rejected by an invariant. For example, `correctBounds` moves a static that overlaps another static (`core/layout.ts:230-232`, C-B9), so "statics never move" does not cover overlapping statics.

| ------------------------------------------------------------------ | ---------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |

### 5. Playwright scenario suite (RGL-06)

- `test/e2e/harness-app.jsx` takes `?scenario=<id>&variant=<v>` and renders the shared scenario definitions from `test/golden-react/`, wrapped in StrictMode when the variant says so. It exposes `window.__rgl = { ready, trace, frames, layout, cellToClient }`.

1. **ctrl+click (RD 4.6.0+).** Accept the "ctrl+left-drag does not start a drag" behavior for all RGL users, or restore the old behavior with an RGL-side override?
   - _Recommendation_: accept it and document it, in both the RD 4.8.0 notes and the RGL 2.4.0 notes. Fresh installs already get it through `^4.4.6`. `allowAnyClick` would also enable right- and middle-button drags.

   - _Recommendation_: yes. It is a publishing decision, so it is listed here rather than decided. Without it, both regressions stay in the shipped version until 2.4.0.
3. **Drop react-draggable and react-resizable for an internal pointer layer?**
   - _Recommendation_: no, not in 2.x. Fix them upstream, ship the 2.5.0 translation functions, build `pointerEventsAdapter` as an opt-in experiment after 2.5.0, and decide for v3 on measured parity, bytes and layout reads (§8).
4. **PR #2260 (cross-grid drag).** Merge before the engine, or rebase it onto the transfer interface (§4, rank 13)?
   - _Recommendation_: rebase after RGL-32 and RGL-36, reusing its hit-testing, ghost, tests and example. Close PR #2267 with a pointer to this RFC, since it targets the v1 tree and renames the package.
5. **Legacy `Responsive` threshold (RX-13a).** Restore v1's 0 px, or keep 2.x's accidental 3 px?

## 14. Security

RGL renders layouts that often come from storage, a server or another user (shared dashboards). This section covers untrusted layout input. The grep in round 1 found no `dangerouslySetInnerHTML`, `eval`, `new Function` or `innerHTML` in `src/`, and no new API takes strings into one. The keyboard live region writes with `textContent` (§4, rank 9).

**Threat.** A collaborator who controls a saved layout can freeze the tab of everyone who opens it. Value bounds alone do not stop this, because several loops do work proportional to the size of a number, not the number of items:

| Loop                                                | Where                                                                                               | Work today                                                                                                                                                                                                                                                             |
| --------------------------------------------------- | --------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Wrap compactor marks static cells one by one        | `for (let dy = 0; dy < s.h; dy++)` (`extras/wrapCompactor.ts:70-74`)                                | `h x w` `Set` entries per static: a static with `h: 1e9` runs a billion iterations                                                                                                                                                                                     |
| Wrap compactor finds the next free cell             | `while (staticPositions.has(nextPos)) nextPos++` (`extras/wrapCompactor.ts:94`)                     | one step per blocked cell. With `cols: 1`, a static at `y: 0, h: 1e9` and one 1x1 item, the first legal row is 1e9 (executor, round 2)                                                                                                                                 |
| `correctBounds` moves overlapping statics down      | `while (getFirstCollision(collidesWith, l)) l.y++` (`core/layout.ts:230-232`)                       | one full scan per row: about h x S^3 / 2 `collides` calls for S statics; 2,107 ms at S = 80, h = 10,000 (skeptic, round 2). A jump past each collider still leaves about n^3 work in the item count: 1,000 overlapping statics took 558 ms on the #2328 head (round 3) |
| `correctBounds` places `y: Infinity` at the bottom  | `l.y = bottom(collidesWith)` (`core/layout.ts:223-225`)                                             | a static at `y: Infinity` keeps the bottom infinite, so the sentinel survives into compaction (pentester, round 3)                                                                                                                                                     |
| Classic compactors move each item toward the origin | `while (l.y > 0 && !getFirstCollision(compareWith, l)) l.y--` (`core/compactors.ts:104`)            | one full scan per row stepped; the start row is `min(bottom, y)` (`:101`), so one tall item makes it large (pentester, round 2). The exported `compactItemVertical` runs the same loop for direct callers                                                              |
| Fast horizontal compactor tracks a tide per row     | `new Array(maxRow).fill(0)` and a step per static row (`extras/fastHorizontalCompactor.ts:124,140`) | memory and work proportional to the tallest item: a direct call with a static `h: 1e9` allocates a billion entries (executor, round 3)                                                                                                                                 |

Non-finite values have a related failure: `collides` returns `true` for NaN (`core/collision.ts:24-27`), so "move until no collision" loops can spin (C-L1).

All of this ships in **2.4.0**: a bound on values at intake (RGL-48), and a bound on work in each loop (RGL-22, RGL-49).

### Intake bounds (RGL-48, 2.4.0)

RGL-48 is in review with RGL-49 as [#2328](https://github.com/react-grid-layout/react-grid-layout/pull/2328). One function, `validateLayoutInput(layout, { cols, maxRows })` in `core/validation.ts`, runs on every path a layout enters by. `react-grid-layout/core` exports it with `MAX_GRID_ROWS` for standalone use, and the README section "Bounds for saved layouts" documents it:

| Path                                                           | Call site (at `1468c0f`)                                                                                                                                    |
| -------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GridLayout` `layout` prop and `data-grid` children            | `synchronizeLayoutWithChildren`, before `correctBounds` (`GridLayout.tsx:282`)                                                                              |
| `ResponsiveGridLayout` `layouts` prop and `data-grid` children | its sync copy (`ResponsiveGridLayout.tsx:189`), behind the ingest gate (`:274`)                                                                             |
| `ResponsiveGridLayout` initial layout                          | before `findOrGenerateResponsiveLayout` (`ResponsiveGridLayout.tsx:237-238`), which corrects and compacts a generated layout (`core/responsive.ts:149,155`) |
| `useGridLayout` initial layout and `setLayout`                 | `react/hooks/useGridLayout.ts:169,199`; the `setLayout` member (`:73`)                                                                                      |
| `useResponsiveLayout` `layouts`                                | behind its ingest gate (`react/hooks/useResponsiveLayout.ts:273`)                                                                                           |
| `useResponsiveLayout` setters                                  | `setLayoutForBreakpoint` and `setLayouts` (`react/hooks/useResponsiveLayout.ts:201,209`)                                                                    |
| Drop item                                                      | `droppingItem` and the `onDragOver` size override in `GridLayout`; `onDropDragOver` in the hook (`useGridLayout.ts:382-393`)                                |
| Legacy wrappers                                                | through the v2 paths above; they add no path of their own                                                                                                   |

Every responsive path validates each stored breakpoint layout with that breakpoint's `cols`, before any generation or compaction reads it. #2328 implements these paths.

**Trust boundary.** Validation runs only on external input: props, the hook setters, `data-grid` fields, the drop item, and stored responsive layouts when the component takes them in. It never runs on the grid's resolved state or on a direct core lookup. Collision resolution may legitimately place items beyond the input row limit, and re-validating resolved state would re-clamp them on every child or breakpoint change. #2328 removed five such resolved-state calls in `5a745531` and pins the rule with child-change and breakpoint-change tests.

In 2.5.0 the same function runs in the binding before `syncProps`, `setLayout` and `start{kind:"drop"}`, so the reducer never sees an unchecked layout.

**Rules.** These are the bounds #2328 ships (`core/validation.ts`, README). `rowLimit` is `MAX_GRID_ROWS` (10,000), lowered by a smaller finite `maxRows`, with a floor of 1. They are constants, not config.

| Field          | Bound                                                                                                                           |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| `w`, `minW`    | `[1, cols]`                                                                                                                     |
| `x`            | `[0, cols - w]`                                                                                                                 |
| `h`, `minH`    | `[1, rowLimit]`                                                                                                                 |
| finite `y`     | `[0, rowLimit]`                                                                                                                 |
| `y: Infinity`  | kept as "place at bottom"; `correctBounds` resolves it against the bottom of the items whose `y` is finite (RGL-49, `dbd1cd7d`) |
| `maxW`, `maxH` | only raised to their minimum (`minW` or `minH`, else 1); larger values, `Infinity` included, pass unchanged                     |

- `NaN`, `-Infinity` and non-numbers take the lower bound. `+Infinity` takes the upper bound, except the `y` sentinel. Fractions are kept. Missing optional limits stay absent.
- `maxW` and `maxH` are not clamped to the grid (`9df78861`). `Infinity` is the documented default, a maximum above the grid causes no work because `w` and `h` are bounded on their own, and clamping would rewrite `Infinity` into every `onLayoutChange` payload and cap a later, wider grid.
- The minimums are bounded because `applySizeConstraints` clamps to them on every resize (`core/constraints.ts:95`). Without that, `minH: 1e9` would produce `h: 1e9` on the first resize, and `minH: NaN` would produce `h: NaN`.
- `x` is clamped into the current `cols`, so an item outside the grid moves inside at intake and `onLayoutChange` fires. That is a changelog item. `correctBounds`' pinned `x: 0, w: cols` rule for a negative `x` (C-B10) is now reached only by direct calls.
- Duplicate ids are kept, as today. #2328 does not check them; RGL-47 adds `RGL_W007` (C-B14).
- An unchanged layout is returned as the same object. A changed one emits one uncoded development `console.warn` per call, none in production. RGL-47, which owns the code registry and `docs/warnings.md`, assigns it `RGL_W002`; #2328 itself emits no code.
- These are intake bounds, not a cap on the final bottom: collision resolution can stack items below `rowLimit`.

In-bounds behavior is byte-identical. Out-of-bounds goldens change, as #2328's commits list: `cols-no-resync.{v2,legacy}`, the four `hook-cols-and-compactor-sync.{normal,strict}-{component,disagreements}` traces, and the core `extras-wrap/known-bug-e-static-infinity-budget`. `responsive/existing` changed in `c678f73d` and was restored in `5a745531`, once validation stopped running on resolved state.

## 15. Release

### Releases and channels

| Release | Contents                                                                                                         | Channel                                                                                 |
| ------- | ---------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| 2.3.1   | RX-1 and RX-2, if approved (open question 2)                                                                     | `latest`, from `release/2.3`                                                            |
| 2.4.0   | Phases 1-4: tests, CI, upstream floors, input and work bounds, core refactors, fixes as golden diffs. No engine. | `2.4.0-rc.N` on `next` for at least one week, then `latest`; patches from `release/2.4` |
| 2.5.0   | Phases 5-7: the engine, the React extraction, the extension points                                               | `2.5.0-rc.N` on `next` for at least two weeks, then `latest`                            |

The release workflow already supports this. It is a `workflow_dispatch` with `prerelease` and `preminor` among its `semver` options and an npm `tag` input that defaults to `latest` (`.github/workflows/release.yml:4-25`). An rc is a `preminor` (then `prerelease`) run with `tag: next`.

There is no dual controller. The engine replaces the old one in 2.5.0. The rc windows and the per-frame pixel checks (RGL-06) are the guard instead. During each rc, the maintainer asks two or three large consumers to run it.

Splitting the releases keeps the Phase 4 fixes revertible on their own: they ship in 2.4.0 before any engine code exists, and each is one PR.

### Promote and abort criteria

The same form for both releases. A clock restarts when a new rc is cut.

|                        | 2.4.0                                                                                                                                                                                                  | 2.5.0                                                                                                                                                                                                                                                                                                                                        |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Minimum time on `next` | 1 week from the last rc                                                                                                                                                                                | 2 weeks from the last rc                                                                                                                                                                                                                                                                                                                     |
| Promote when all hold  | No open issue labeled `2.4-rc` (regressions reported against the rc). The CI matrix is green on the release commit. The Chromium per-frame suite is green. At least one named consumer reported a run. | No open issue labeled `2.5-rc`. The CI matrix is green. The per-frame suite is green in Chromium, WebKit and Firefox. The manual touch-delay check passed on iOS Safari and Android Chrome (§4 rank 8). At least one consumer reported a run.                                                                                                |
| A regression in the rc | Fixed forward in the next rc, which restarts the clock                                                                                                                                                 | Fixed forward in the next rc, which restarts the clock                                                                                                                                                                                                                                                                                       |
| Abort                  | Do not promote. `latest` stays on 2.3.x. Point `next` at the last good rc (or remove it) and `npm deprecate` the aborted rc. Fix forward.                                                              | Do not promote. `latest` stays on 2.4.x, patched from `release/2.4`. If the engine must leave master, the whole stack is reverted in one PR back to the 2.4.0 code; single engine PRs are never reverted alone, because each builds on the one before. The engine is then re-planned. `next` and the aborted rc are cleaned up as for 2.4.0. |

The rc issue names the consumers asked to run it, because silence from a client library mostly means nobody ran it. The `2.4-rc` and `2.5-rc` labels are created when the first rc of each release is cut.

The promotion commit is the last rc commit plus the version bump, with no merge in between, so `latest` ships the code the rc tested. `release.yml` takes `semver` and `tag` as independent inputs (`.github/workflows/release.yml:4-25`), so one forgotten field could publish an rc to `latest`; RGL-45 adds a guard step that fails when the version contains `-` and the tag is `latest`. After promotion there is no rollback, only fix-forward: a bad 2.4.0 or 2.5.0 is followed by a 2.4.1 or 2.5.1 that fixes or reverts, plus `npm deprecate` on the bad version. Moving the `latest` tag back is not relied on, which is why the rc window is the real gate.

### Hotfix branch

When the first 2.5.0 engine PR (RGL-23) merges, cut `release/2.4` from the 2.4.0 tag. From then on, 2.4.x patches land on `release/2.4`, publish from there, and are cherry-picked to master. Master carries engine work until 2.5.0 is promoted, so it is never the source of a 2.4.x patch. The release workflow is rehearsed from `release/2.4` when the branch is cut, to confirm which base branch the release automation opens its PR against, so the first real use is not during an incident. Open question 2 asks whether to cut 2.3.1 from `release/2.3` now.

### Pixel checks

The per-frame bounding boxes are committed JSON (RGL-06), rounded to 0.01 px and recorded on the Linux CI image, so "byte-identical" for pixels means equal to that JSON. 2.4.0 runs them in Chromium only, because 2.4.0 does not change the pixel path: there is no engine, and RX-1 is already fixed on master (`1468c0f`), with this suite guarding it. A WebKit and a Firefox project each add a full e2e run per CI job, and Firefox has a known drop-path divergence to triage first (RX-11d). The engine release is where browser differences matter, so RGL-24's first commit adds both projects and records their JSON on the 2.4.x code, before the engine lands, and the engine commits must leave it unchanged. A frame is one sample after each awaited `page.mouse.move` settles, and only the recorder job writes the JSON (RGL-06).

### Errors in production

- A caught strategy error (§3 events) goes to `onError` when passed. Without it, the binding calls `console.error` once per error source per grid, in development and production alike, through `reportOnce` in `core/dev.ts`. Strategy errors are third-party bugs and rare, and a silent veto leaves an item that will not move with nothing in the console.
- `RGL_W005` (an invalid strategy result) uses the same production path.
- `createInitialState`, `syncProps`, `setConfig` and `setLayout` catch, report and keep the previous state. `createInitialState` keeps the validated input layout without compaction.
- Every other warning is development only, through `devWarn`.

### Upstream gating

RD and RR publish outside RGL's release train, and a caret range picks them up on any fresh install (`package.json:111-112`). So each upstream release follows this order:

1. RGL-05, RGL-07 and RGL-08 are merged and green.
2. The RD or RR release is published to the `next` tag.
3. A `workflow_dispatch` job in RGL, `.github/workflows/upstream-candidate.yml` (added in RGL-07), takes the package name and dist-tag. It checks out RGL master, runs `yarn add react-draggable@next` (or `react-resizable@next`), and runs the contract, interaction-golden and SSR suites, Playwright smoke and `live-interaction.spec.ts`. It does the same on `release/2.4` once that branch exists, which is the 2.4.x line. For an RD candidate, a third leg checks out the latest 2.3.x release tag, installs `react-draggable@next`, and runs that tag's own test suite.
4. Only when both runs are green does `latest` move. The RD and RR release PR templates carry this as a checklist line with a link to the run.

2.3.x is out of the RR gate only: it pins `react-resizable ^3.2.0` (`package.json:112`), so no RR 4.x candidate can reach it. It declares `react-draggable ^4.4.6` (`package.json:111`), so every RD 4.x release reaches it on a fresh install, and the floor-versus-latest cells cannot cover that, because they run master's code. That is why the RD gate has the third leg above.

RD-02 (the `offsetParent` cache) ships in its own RD release after 4.8.0, so a bad cache reverts without reverting the fixes.

### Golden diffs and changelog

- The golden suites fail on any changed or missing fixture in an ordinary run; only `GOLDEN_UPDATE=1` writes them.
- The PR template (`.github/PULL_REQUEST_TEMPLATE.md`, RGL-45) gains four checklist lines: "golden diffs explained, each fixed bug's `knownBug` tag removed", "CHANGELOG entry for every expected diff", "`baseline.json`, the API report or the consumer fixtures changed: why (no PR after RGL-46 edits `test/types/consumer-2.3`)" and "new runtime APIs stay within ES2020". The last one holds because CI runs one Node version while consumers render on the server with older ones.
- Every job runs on the Node in `.nvmrc`. The global timsort patch (`test/util/setupTests.js:5-9`) changes tie order, so fixtures with `y: Infinity` or NaN, where comparators return NaN, are flagged in the corpus.
- There is no trailer-parsing or changelog script and no CODEOWNERS file. The repo has one maintainer, so CODEOWNERS adds no second reviewer, and a script could only check that a sentence exists, not that it is true. The tradeoff: a careless golden update is caught by review alone.
- The 2.4.0 and 2.5.0 notes open with a "Behavior changes" section. Every §7 row with "Breaking if fixed" other than "No", and every §12 row, maps to one entry. The release PR checks the mapping row by row.

## Alternatives Considered

### 1. Fix the bugs in place and keep three state machines

Rejected:

- Every bug in rgl-react §4 would need fixing in `GridLayout`, then again in `useGridLayout`, which has already drifted (RX-9).
- No extension point in §4 could ship once.
- The golden masters would still help, but the engine replay differential would not exist.

### 2. A generic plugin registry (`plugins={[...]}`)

Rejected:

- The pluggability survey found no demand that typed strategy slots cannot meet (pluggability §3).
- ProseMirror and TipTap show the cost: priority ordering, lifecycle hooks and cross-plugin state (pluggability §5).
- RGL's existing `LayoutConstraint[]` already gives ordered composition without a registry.

### 3. Engine as a class (gridstack's `GridStackEngine` model)

Rejected:

- A reducer over plain data is easier to replay, diff and freeze in tests.
- It maps onto `useSyncExternalStore` without an adapter.
- gridstack's lesson, separating the engine from the DOM, is kept (pluggability §5).

### 4. Replace react-draggable and react-resizable now

Rejected for 2.x (§8):

- The savings are small: about 15 KB gzip, unminified.
- Fixing the known defects upstream is cheaper.
- An internal layer would give up 310 existing tests across the two repos.

### 5. A new major (v3) instead of minors

Rejected:

- Nothing here needs a breaking change.
- Shipping as minors gets the fixes to every 2.x user.
- Breaking cleanups (freezing defaults, dropping wrappers, `data-grid` on v2) are collected for v3 in §12 and §13.
